# 徒歩・走行 距離ゲーム 仕様書

## 0. 概要

スマートフォンで徒歩・走行(人力移動)を検知し、移動距離に応じて経験値(XP)が貯まるAndroidゲーム。

- **最終目標**: 地球一周(40,075km)を歩く・走ることで踏破する
- **進行の柱**: 100個のマイルストーン(いずれも実在する建造物・地形・記録などの距離になぞらえたもの)を、距離が短い順に達成していく
- **2周目以降**: 100マイルストーンの再提示はせず、周回カウンター+周内マーカーのみのシンプルな仕組みに切り替える
- **対象プラットフォーム**: Android(将来的な拡張は本仕様の対象外)
- **ビジュアル方向性**: 全体的にドット絵(ピクセルアート)

---

## 1. 検出・計測ロジック

### 1.1 活動判定

Android の **ActivityRecognition API** を使用し、`ON_FOOT`(徒歩・走行の総称)のみをXP対象とする。徒歩と走行は区別しない(人力移動かどうかのみを見る)。

| 状態 | 判定 |
|---|---|
| 静止 | 速度0〜1.5km/h かつ 直近数秒の位置のばらつきが小さい |
| 人力移動(XP対象) | `ON_FOOT`の信頼度が概ね50%以上、速度は概ね25km/h以下 |
| 自転車・乗り物(対象外) | `ON_BICYCLE`/`IN_VEHICLE`判定、または持続的に25km/h超 |

自転車はXP対象外。速度閾値は主に異常値の足切り用の補助シグナルとして使う(判定の主軸はActivityRecognition APIの分類結果)。

### 1.2 GPS取得間隔とバッテリー

常時バックグラウンドで動作し、歩けば自動でXPが貯まる方式を前提とする。

- **静止中**: GPSはほぼ停止。Activity Transition API(`STILL`→`ON_FOOT`の遷移をOS側からプッシュ通知させる仕組み)で移動開始を検知し、そのタイミングでGPSを起動する
- **移動中**: `PRIORITY_BALANCED_POWER_ACCURACY`で5〜10秒間隔(直線移動が多ければ10秒、街中でカーブが多ければ5秒寄り)
- **並行稼働**: `TYPE_STEP_COUNTER`(低消費電力センサー)を常時ONにし、GPSが拾えない状況の歩数ベース計測に備える

### 1.3 屋内・GPS圏外時の歩数フォールバック

- **発動条件**: 位置更新が15〜20秒程度途絶える、または`accuracy`が50m超になったら切替(短時間の瞬断で頻繁に切り替わらないよう、ここにも短いヒステリシスを設ける)
- **歩幅の自己較正**: GPSが取得できている間、「実測歩幅 = GPS移動距離 ÷ 歩数」を継続計算し移動平均で個人の歩幅を自動キャリブレーション。フォールバック時はこの値を適用する(身長入力は不要)
- **`TYPE_STEP_COUNTER`の注意点**: 端末再起動でカウンタが0にリセットされる仕様のため、前回値との差分がマイナスになったら「再起動があった」と判定しベースラインを補正する処理が必須
- **モード切替時**: 切替の瞬間に歩数カウンタ値とGPS距離の起点を記録し、二重カウント・欠落を防ぐ

### 1.4 停止判定

- **停止確定**: GPS速度が1.5km/h未満、かつ歩数センサーで新しい歩数増加が無い状態が2〜3秒連続したら「停止」と確定(速度と歩数の両条件で、GPSの瞬間的なジッターによる誤停止判定を防ぐ)
- **遡及除外**: 停止確定時点から過去2〜3秒分のGPS距離加算を取り消す(GPSノイズは停止直前から出始めることが多いため。歩数ベースの距離は元々「歩いた分しか増えない」ためこの処理は不要)
- **再開判定**: 停止と対称に、速度が徒歩域に戻り新しい歩数が検出される状態が2〜3秒続いたら再開(同様にヒステリシスを設ける)
- **長時間の停止(信号待ち等)**: 特別な閾値は不要。停止が続く限りカウント停止を継続するだけでよい
- 現状は「生涯累計距離」のみを追う設計とし、1回の外出ごとの「セッション」概念(タイムアウトで自動終了等)は導入しない。将来的にセッション単位のUIが必要になった場合は別途タイムアウト値を設計する

### 1.5 異常値・不正対策

ON_FOOT判定(1.1)で大枠は担保済み。ここでは「GPSノイズによる瞬間ジャンプ」と「意図的なGPS偽装」を弾く。

- **区間速度の上限フィルタ**: 前後2点間の瞬間速度が30〜40km/hを超えたら、その区間は距離加算しない(安全側の最終防波堤)
- **前後点との整合性チェック**: A→B→Cで、AB間・BC間はどちらも速すぎるがAC間は正常、というケースはBを外れ値として除外し、A→Cを直接距離計算する
- **精度フィルタ**: `Location.getAccuracy()`が30m超の点は距離計算から除外、または重みを下げる
- **モック位置対策**: `Location.isFromMockProvider()`でモック位置プロバイダを検出し、該当区間はXP対象外にする
- **ソフトな日次上限**: 1日の累積距離に非現実的な上限(例: 100km/日)を設け、超えた分はXP計算を一時停止してログに残す
- ランキングや称号などの対人競争要素がないため、上記以上の不正対策(サーバー側検証等)は過剰と判断し導入しない

## 2. 経験値(XP)

### 2.1 距離→XP換算

徒歩・走行を区別しないため、走行時倍率などの補正は無し。

- **換算式**: 1m = 1XP (1km = 1,000XP)
- 地球一周(40,075km)は 40,075,000XP
- km単位のままだと短い外出で端数XPになり達成感が薄いため、m単位の整数XPとする

### 2.2 XPの用途

XPは距離の進捗表示専用。マイルストーン到達以外の消費先(称号解放・ショップ等)は持たない。貯まる一方の累計値のみを保持すればよく、残高管理は不要。

## 3. 100マイルストーン

### 3.1 設計方針

- 各マイルストーンに、建造物の高さ・トンネル・橋・運河・巡礼路・川・山脈・国境線・鉄道・道路・海峡・天体・動物の渡りなど、**実在するもの100個**を割り当てる
- 距離配分は数式のカーブを先に決めて当てはめるのではなく、実在する100個の距離を**実際の距離が小さい順に**1番から100番まで並べた結果として決まる(結果的に序盤ほど間隔が狭く、終盤ほど間隔が広がる)
- 100番目は実在物のリストからではなく、当初からのゴールである**地球一周(40,075km)そのもの**に固定する
- 海峡の幅・山脈の全長・国境線などは資料によって数値に幅があるため「約」の概算値
- 名称・選定は仮案であり差し替え可能。97番(22,117km)と98番(35,000km)の間はやや距離が空いている(この帯に収まる有名な実在距離が未発見のため)

### 3.3 報酬設計

- **バッジ**: マイルストーン到達ごとにコレクションへ追加されるスタンプ
- **ランク**: 銅→銀→金→プラチナ→伝説の5段階(バッジの見た目の枠として表現)
- 上記2層のみ。称号(タイトル)は導入しない(他ユーザーと競うネットワーク機能を持たないため、称号を「誰に見せるためのものか」が曖昧になる)
- ショップ・消費アイテムは導入しない(XPを進捗表示専用とした方針と一貫させ、バランス調整や在庫管理が発生する消費系システムを持ち込まない)

### 3.4 達成時の演出・通知仕様

**通知(バックグラウンド達成時)**
- Android通知で「🎉[マイルストーン名]に到達」を表示、タップでアプリ内の達成演出画面へ遷移
- 複数を一度に達成した場合は個別通知を連発せず「まとめて3個達成」のように集約する

**アプリ内演出(ランク別)**
- 銅・銀: バッジがコレクションに加わる軽いアニメーション+効果音のみ
- 金・プラチナ: 紙吹雪等のパーティクルエフェクト+効果音を追加
- 伝説: フルスクリーン演出、地球儀/マップのカメラワーク、その実在物についての一言説明を表示

**演出内で表示する情報**: バッジ画像/マイルストーン名/ここまでの累計距離/次のマイルストーンまでの距離

## 4. 周回(2周目以降)

### 4.1 周回カウンターの見せ方

- ホーム画面に「2周目」のようなシンプルな数字表示のみ(1周目の100マイルストーン一覧のような重い仕組みは持ち込まない)
- 「生涯累計距離」と「今の周の進捗距離」を併記する(例: 2周目 12,400km / 40,075km)

### 4.2 周内マーカー(25/50/75%)

どの周でも同じ距離のため、1回設計すれば全周回で使い回せる。

| 到達率 | 距離 | 演出 |
|---|---|---|
| 25% | 約10,019km | 「赤道から北極点までの距離に相当」(メートル法制定時の定義そのもの、という豆知識付き) |
| 50% | 約20,038km | 「地球の裏側(対蹠地)に到達」演出 |
| 75% | 約30,056km | 節目演出のみ(この距離帯は100マイルストーンリストの高距離帯と被るため、数字のインパクトのみで見せる) |
| 100% | 40,075km | 周回数+1、次の周へ |

### 4.3 周回ごとの見た目バリエーション

- 1・2・3・5・10・20・50・100周目の8段階でトレイル色/地球儀スキンが変化、それ以降は100周ごとに新色を追加
- 8段階は初期リリースの目安。素材制作の余力に応じて増減可

## 5. ビジュアル・UI(ドット絵)

### 5.1 マップ表現

- **MVP**: 2D正距円筒図法の世界地図をドット絵化(SFC/GBA時代のRPGワールドマップ風)。移動距離に応じて光る軌跡ラインが伸び、地図の右端に到達したら左端に繋がって伸び続けることで「世界を回っている」感覚を表現する
- トレイルラインは滑らかな曲線ではなく、階段状のドットラインで描画する
- **3D化は将来検討**: 核となるゲームループ(歩く→XPが貯まる→楽しい)の手応えを先に確認してから、3D回転地球儀への差し替えを検討する。先に3Dへ投資するとループ自体の検証が遅れるリスクがあるため
- 伝説ランクのフルスクリーン演出など「ここぞ」の場面だけ、動画/Lottieアニメーションを1〜2種類用意し部分的にリッチに見せる

### 5.2 バッジ/アイコンの制作方針

- 「ランク5段階の枠」×「カテゴリ別モチーフ15種程度(建造物・トンネル・橋・運河・巡礼路・川・山脈・国境・鉄道・城壁・宇宙・航空路線・動物・海峡・大陸など)」の組み合わせで100個をカバーする。実際に描き起こすアセットは20点程度で済む
- ドット絵は32×32px程度の固定グリッド+限定パレットで統一感を出す(AI画像生成でも「ドット絵、32×32、○○のモチーフ」という指定で安定して狙った絵が出やすい)

### 5.3 サウンド・アニメーション

ランク単位で共通化し、100個分は用意しない。

- 銅・銀: 効果音1種+軽いスケールアニメーション
- 金・プラチナ: 効果音1種+紙吹雪等のパーティクル(粗めの四角ドットパーティクルでドット絵の統一感を保つ)
- 伝説: 専用効果音+フルスクリーン演出1種類(全ランクで使い回す)
- 効果音はフリー素材(効果音ラボ等)から4種類程度を選定する

### 5.4 UI全体への拡張と実装上の注意

- ボタン・フォント・プログレスバーなどのUIパーツもドット絵アイコン+ドットフォント(例: Press Start 2P)で統一する
- **実装注意**: `ImageView`の既定はバイリニア(平滑化)スケーリングのため、そのまま拡大するとドット絵がぼやける。アンチエイリアスをオフにする、またはニアレストネイバー方式での拡大設定が必須

## 6. データ設計・引き継ぎ

### 6.1 DBスキーマ(Room)

```
daily_log
 - date (PK, "2026-08-19"形式)
 - distance_m
 - updated_at

lifetime_stats (1行のみ)
 - total_distance_m
 - current_lap
 - stride_length_cm  (自己較正した歩幅)

milestone_achievement
 - milestone_index (PK, 1〜100)
 - achieved_at
 - distance_m_at_achievement

lap_record
 - lap_number (PK)
 - completed_at
```

生のGPS座標列は永続保存しない。日別距離に集計した時点で破棄する(1.4の遡及除外用に直近数秒分だけ一時保持するのは別枠)。

### 6.2 クラウド同期方式

ランキング等のネットワーク機能を持たないため、同期の目的は「機種変更時の個人バックアップ」のみ。

- **採用**: Google DriveのAppDataFolder(ユーザーの通常のDrive画面には表示されない専用領域にJSON1ファイルを置く。サーバー運用が不要で個人開発と相性が良い)
- Firestore等のリアルタイムDBは今回の用途にはオーバースペック(バックエンド運用コストが発生するため不採用)

### 6.3 JSONエクスポート/インポート形式

DBスキーマをそのままシリアライズする。手動エクスポート機能とクラウド同期の両方で共用する。

```json
{
  "schema_version": 1,
  "exported_at": "2026-08-19T12:00:00Z",
  "lifetime_stats": {
    "total_distance_m": 12345678,
    "current_lap": 1,
    "stride_length_cm": 68.5
  },
  "daily_log": [
    {"date": "2026-08-01", "distance_m": 5230}
  ],
  "milestone_achievements": [
    {"milestone_index": 1, "achieved_at": "2026-08-01T09:15:00Z"}
  ],
  "lap_records": [
    {"lap_number": 1, "completed_at": null}
  ]
}
```

`schema_version`により、将来テーブル構成が変わっても古いバックアップを読み込めるようにする。

### 6.4 端末間の競合解決ルール

単純な合算は同じ外出の二重カウントを招くため避ける。

- `daily_log`: 日付をキーとし、同期時に同じ日付のレコードがあれば**距離が大きい方(max)を採用**
- `milestone_achievement`・`lap_record`: 両端末の内容を**和集合でマージ**。達成日時が両方にあれば早い方を採用
- `total_distance_m`: 日別ログの合計から**再計算**する(端末ごとの累計値を直接比較・合算しない)
- トレードオフ: 2台を同時に持って同じ散歩を計測した場合は過小評価になり得るが、二重カウントよりは安全側

## 7. 権限・不正対策・初期設定

### 7.1 位置情報/フォアグラウンドサービス権限(Androidバージョン別)

1. 初回、`ACCESS_FINE_LOCATION`+`ACCESS_COARSE_LOCATION`を「使用中のみ許可」でリクエスト
2. バックグラウンド計測が必要な理由を画面で説明してから、`ACCESS_BACKGROUND_LOCATION`を別リクエスト(Android 11以降、システムダイアログで直接「常に許可」を選べない機種が多く、設定画面への誘導が必要)
3. **Android 13+**: 通知権限(`POST_NOTIFICATIONS`)もリクエスト(マイルストーン達成通知に必須)
4. **Android 14+**: マニフェストで`FOREGROUND_SERVICE`+`FOREGROUND_SERVICE_LOCATION`を宣言し、Serviceに`foregroundServiceType="location"`を指定(必須。未対応だと`SecurityException`でクラッシュ)
5. **Android 15+**: バックグラウンドからのフォアグラウンドサービス起動制限がさらに強化されているが、「ユーザーがアプリ内で計測開始を押す→その流れでフォアグラウンドサービスを起動」という本設計は正規の例外条件に該当するため問題ない
6. `ACCESS_BACKGROUND_LOCATION`を使うアプリはGoogle Play審査で用途の明示(プライバシーポリシー、アプリ内での目立つ説明)が必要。フィットネス系アプリとして一般的に承認される用途だが、審査対応は事前に見込んでおく

### 7.2 バッテリー最適化除外を促すUIフロー

- 初回チュートリアル完了時に除外を促す画面を1枚挟み、`Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`インテントで設定ダイアログを直接呼び出す
- 拒否されても計測自体は動作する設計とする(強制不可のため)。ただし拒否時はバックグラウンド計測が中断されうる旨を伝える
- 端末メーカー独自の電力管理(Xiaomi/Huawei等)は個別対応が困難なため、初期リリースでは対象外とする

### 7.3 GPS偽装対策

1.5節の`isFromMockProvider()`チェック+ソフトな日次上限で十分と判断(対人競争要素がないため、これ以上の対策は過剰)。

### 7.4 初期設定・チュートリアル

- 歩幅は自己較正方式(1.3)のため、身長入力等の個人パラメータ入力は不要
- 権限リクエストが複数ステップにわたるため、各ステップの直前に「なぜ必要か」を1枚ずつ挟む3〜4枚程度の簡単なオンボーディングを用意する(ゲームルールの説明+権限の説明を1セットずつ)
